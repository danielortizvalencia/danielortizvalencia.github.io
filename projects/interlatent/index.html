Driving robots from a headset, and measuring the loop that carries it

I helped build the hardware and software infrastructure for deploying frontier models on physical robots. This page covers the teleoperation path and the instrumentation I added to find out whether it holds its timing on the hardware it actually runs on.

In Short

Deploying frontier models onto robots that actually move

Two pieces of work: the operator path that lets a human drive an arm in VR and have every episode land as training data, and the validation campaign that went looking for where the curation agents break. Both write-ups below are carried over from my engineering portfolio unchanged.

I · Teleoperation

Operator control across arms that disagree about everything

Meta Quest / WebXR, browser IK, WebTransport over QUIC, CAN, Jetson & Raspberry Pi

Background

  • Collecting robot demonstrations required a responsive operator interface across arms with different kinematics, joint units, gripper ranges, and camera setups. SO-101 uses degrees, YAM uses radians, and NORI uses a normalized joint scale; those differences had to be handled explicitly.
  • The system also had competing timing requirements: operator commands and camera previews needed to stay fresh, while recorded observations and actions needed to arrive intact for later training.

Technical Approach

  • Hardware bring-up and calibration. I worked through robot drivers, dedicated CAN channels, camera placement, USB bandwidth and power budgets, and host setup on Raspberry Pi 5 and NVIDIA Jetson. I validated the VR-to-IK path in MuJoCo before live hardware testing, checking clutch engagement, joint movement, gripper response, and independent arm control.
  • Controller pose to joint targets. The Quest browser reads WebXR controller poses. Clutch-relative mapping anchors motion to the robot's current pose; damped least-squares IK then computes joint targets from the robot's kinematic model. Frame alignment, tool offsets, damping, and velocity caps determine whether hand motion produces stable, intuitive robot motion.
  • Fresh commands over an imperfect network. Browser and robot dial out to a nearby relay, which pairs them by session and forwards bytes. Repeated QUIC datagrams carry joint targets; sequence numbers remove duplicates and stale commands. Applied-sequence echoes measure command round-trip time using the browser's own clock. Each preview JPEG gets an independent stream so one delayed frame does not stall later frames.
  • Safety at the motors. A command arbiter selects e-stop, teleoperation, hold, or policy control. The node checks freshness, deadman state, joint limits, and velocity, then applies a final per-step clamp before sending actions. Operator takeover flushes queued policy actions so old commands cannot execute after handback.
  • Recording without blocking control. State, executed actions, camera frames, and control-source labels travel on a separate, paced gRPC uplink. A disk spool retains ticks until acknowledgement; the recorder packages them into LeRobot episodes. I also traced stop-to-ready delays to deferred video transcoding and compared live encoding, asynchronous completion, and GPU offload by cost, latency, and implementation risk.
  • Measure each stage. I compared headset and node logs, separating capture time, command time, frame age, loop timing, and missed deadlines. This exposed cases where a near-30 Hz average concealed poor timing headroom or an operator preview falling behind.

Conclusion

  • Helped integrate a shared teleoperation and recording workflow across different robot embodiments, with hardware-specific configuration and a common execution path.
  • In the measured YAM sessions, Raspberry Pi and Jetson both averaged about 29 Hz, but the Jetson configuration missed more control deadlines. I documented the difference and recommended checking power/thermal settings and moving capture work off the control thread. These runs compared complete configurations, not isolated processor performance.
II · Agent Validation

Finding where the curation agents break

Dataset curation agents, visual grounding, temporal consistency & reproducible evaluation

Background

  • Interlatent's agents inspect robot recordings, describe task progress, and create annotations used to curate training datasets. A plausible answer is not enough: an incorrect outcome label or unstable phase boundary can change which demonstrations a policy learns from.
  • I designed a validation campaign to find where these agents break, covering visual hallucinations, temporal drift, repeatability, cost, and unintended changes to stored annotations.

Technical Approach

  • Controlled dataset comparisons. I selected two cloth-folding datasets with different episode lengths and a cable-untangling dataset. This separated sensitivity to clip length from sensitivity to task semantics, while keeping the camera-based manipulation setting comparable.
  • Eight test areas. The test matrix covered ingest and scale, grounding, temporal phases, determinism, project curation, cost and latency, write safety, and generalization. Each check had an explicit prompt, pass criterion, targeted failure mode, and recorded observation.
  • Verify against the recording. I checked answers by scrubbing camera views and examining state tracks, tested false premises, asked the agent how many frames it inspected, and repeated segmentation and outcome prompts on the same episode.
  • Test the full workflow. I tracked tool behavior, annotation versions, cancellation, and cost alongside answer quality. This caught failures that a text-only evaluation would miss, including a description request creating annotations and interrupted jobs continuing to write.
  • Make grading task-aware. In separate episode analysis, I found that short-window progress scores could contradict a successful full episode. I proposed separating terminal success from phase-relative progress, supplying elapsed time and prior-window context, and checking repeated grades before using them to filter data.

Conclusion

  • Produced an evidence-backed limits log and prioritized recommendations: require visual evidence for observational claims, make annotation writes atomic, propagate cancellation to the underlying job, and stabilize repeated segmentation.
  • The tests distinguished reliable behavior from fragile behavior: the same folding episode received a stable success verdict across three checks, while its phase segmentation changed substantially. That distinction matters when deciding which outputs can be trusted for dataset curation.

The through line from here to the rest of my work is the same one: a learned system is only as good as the evidence you are willing to gather about it, and most of that evidence has to come from the hardware it actually runs on.
